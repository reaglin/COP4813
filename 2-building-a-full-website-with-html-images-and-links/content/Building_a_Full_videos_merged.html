Introduction to Multi-Page Website Structure

Introduction

A multi-page website is simply a collection of HTML documents that live together in an organized folder and are connected to each other through links. Instead of putting everything on one long page, you separate content into purposeful pages — a home page, an about page, a contact page — and give visitors a consistent way to move between them. Before you write any HTML, though, you need a plan: what pages exist, what each page is for, what files and folders hold them, and how the navigation ties it all together.

In this course, this topic is the foundation for everything else in Module 2. HTML is the structural layer of the web: elements like header, nav, main, section, article, and footer describe what each part of a page means, not just how it looks. Semantic markup matters because it makes your pages easier for other developers to read, easier for search engines to interpret, and far more usable for people relying on screen readers. Internal links, written as relative paths, are what turn a pile of separate HTML files into a single coherent site.

The videos below focus on the planning and structuring habits that come before and around the code. As you watch, look for the ideas you can transfer directly to a website project: how to break a project into pages or components, how to decide on a folder and file organization, how to sketch structure before building, and how to keep naming and layout consistent. The specific tools and languages shown may differ from plain HTML, but the planning discipline is the same.

Semantic HTML Markup

Introduction

Semantic HTML is the practice of choosing elements that describe the meaning of your content rather than just its appearance. Instead of wrapping everything in generic div elements, you use header for introductory content, nav for navigation links, main for the dominant content of the page, section and article for grouped and self-contained content, and footer for closing information. The markup still looks similar in a browser, but it now carries meaning that software can interpret.

This matters in COP4813 because the website you build in this module is not just a visual artifact. Screen readers use semantic landmarks to let users jump directly to navigation or main content, and search engines use document structure to understand what a page is about. Starting with clean semantic structure also makes your CSS and JavaScript work in later modules far easier, because the structure already reflects the logic of the page.

As you watch the videos below, pay attention to three things: which element is appropriate for each region of a page, how the same page can be built semantically or non-semantically with very different results for accessibility, and how a designer's mockup can be translated into a structural outline before any code is written. Try sketching the semantic outline of your own module project page and compare it with the examples you see.

Embedding Images in HTML

Introduction

Images turn a plain document into a real web page, and in HTML they are added with a single, self-closing element: img. Unlike paragraphs or headings, the img element has no content between tags — everything it needs comes from its attributes. The src attribute points to the image file, alt describes the image for people who cannot see it, and width and height tell the browser how much space to reserve while the page loads.

This matters in COP4813 because the site you build in this module must work for everyone and must not break when files move. A src path that is correct on your machine but wrong on the server produces a broken image; a missing or careless alt attribute makes your page unusable with a screen reader. You will also need to make sensible choices about file formats — JPEG for photographs, PNG for graphics needing transparency, SVG for logos and icons, and newer formats such as WebP for smaller file sizes.

As you watch, pay attention to three things: how relative paths are written when images live in a subfolder like images/, how each speaker decides what alt text should actually say (including when it should be empty), and why setting dimensions in the HTML or CSS helps page layout and performance. Try each example in your own editor rather than only watching.

Creating Hyperlinks

Introduction

Hyperlinks are what turn a collection of separate HTML files into an actual website. The anchor element, written as a pair of <a> tags, wraps the text or image a visitor clicks, and its href attribute tells the browser where to go. That destination can be an absolute URL pointing to another site on the web (an external link), or a relative file path pointing to another page in your own project folder (an internal link).

In this module you are building a multi-page site, so linking is the glue that holds your work together. Every page you create needs to be reachable from your navigation menu, and every navigation menu needs correct relative paths that still work when files move into subfolders. You will also meet the target attribute, which controls whether a link opens in the same tab or a new one, along with the rel attribute that should accompany target="_blank" for security reasons.

As you watch the videos below, pay attention to three things: the exact syntax of the anchor element and where the clickable text goes, the difference between a full URL and a relative path, and the practical habits that keep links from breaking. Try typing each example yourself rather than only watching, and test every link in a browser before you move on.

Internal Navigation and Site Linking

Introduction

A website becomes a website — rather than a pile of separate files — when its pages are connected. Internal navigation is the system of links that lets a visitor move from the home page to an about page, a gallery, or a contact form and back again without ever typing a URL. The core tool is the anchor element, and the skill that makes it work is writing correct relative file paths: addresses that describe where a file sits in relation to the page currently being viewed.

In this topic you will practice writing links such as about.html, pages/contact.html, and ../index.html, and you will see why a path that works on one page may break on another once files are moved into folders. You will also build a navigation menu — a group of links, usually inside a nav element, repeated in the same place and same order on every page so users always know where they are and what their options are. Finally, you will use fragment identifiers (the # syntax paired with an element id) to jump directly to a section within a long page.

As you watch the videos below, pay attention to three things: how the href value changes depending on where the file lives, how the folder structure of the site is organized before any links are written, and how a navigation block is copied and kept consistent across pages. Keep a small test site open and try each path yourself — broken links are usually a typo or a wrong folder level, and the fastest way to learn the rules is to break and fix them.

External Links and Web Resources

Introduction

Linking outward is what makes your site part of the web rather than an island. When you point to a page on another site, you need an absolute URL — the full address including the scheme (https://), the domain, and any path — because a relative path would only ever be resolved against your own site's folders. This topic covers how to write those links with the anchor element and how to choose attributes that affect where the page opens and how safely.

Two attributes matter most here. The target attribute (commonly target="_blank") controls whether the destination replaces the current page or opens in a new tab, and historically a new tab could give the destination limited scripting access back to your page, which is why rel="noopener noreferrer" is the standard companion. The rel attribute also describes the relationship between your page and the destination more broadly, with values such as nofollow, external, and license. Alongside the technical details, there is a user-experience obligation: link text should tell people where they are going, and users should not be surprised by a tab opening unexpectedly.

As you watch, focus on three things: the exact anatomy of the anchor tag (href, text content, closing tag), how the videos distinguish absolute from relative URLs, and any mention of target or rel. Note that short beginner tutorials often stop before the security discussion — treat the module readings as the authority on rel="noopener noreferrer" and use the videos to build fluency with the markup itself.

Bringing It All Together: Building a Complete Website

Introduction

Up to this point in the module you have practiced individual HTML skills: writing semantic elements, placing images, and creating links. This topic asks you to combine those skills into a single, working multi-page website. That means deciding what pages your site needs, naming files and folders consistently, repeating the same semantic structure and navigation menu on every page, adding images with meaningful alt text, and wiring the pages together with relative links while pointing outward with absolute URLs.

This matters because real websites are judged as a whole, not as isolated code snippets. A visitor notices immediately when a navigation link is broken, an image fails to load, or one page looks structurally different from the rest. Planning your folder layout before you start writing HTML, and testing every link and image when you finish, is what turns a pile of files into a site.

The two videos below approach the idea of a complete site from different angles. The first reviews the HTML content elements you will place inside your pages; the second shows a no-code site builder so you can see how pages, navigation, and media fit together conceptually before you hand-code the same ideas. While watching, pay attention to structure and organization rather than to any single tag: ask yourself how each page relates to the others, where files would live on disk, and what you would need to check before calling the site finished.
