Introduction to the DOM and Dynamic Manipulation

Introduction

When a browser loads an HTML file, it does not simply display the markup — it builds an in-memory model of the page called the Document Object Model, or DOM. The DOM represents every element, attribute, and piece of text as a node in a tree, and it exposes those nodes to JavaScript as objects with properties and methods. This is what makes a page programmable: once the tree exists, your code can find a node, read it, change it, add new nodes, or delete them, and the browser immediately re-renders the result.

This topic is the foundation for everything else in Module 12. Before you can create elements with createElement(), restyle them through classList, or wire up event listeners, you need a clear mental picture of the tree and of how JavaScript reaches into it. You will also want to be comfortable with the distinction between a static page (HTML as authored and served) and a dynamic page (HTML as modified at runtime by script), because that distinction explains why the DOM — not your source file — is the thing you are actually manipulating.

As you watch, look for three things. First, how the presenter maps HTML markup onto tree nodes — parent, child, and sibling relationships. Second, which methods are used to select elements (getElementById, querySelector, querySelectorAll, and the older collection-returning methods) and what each one actually returns. Third, how content is read and written through properties such as textContent, innerText, and innerHTML, and what the practical differences between them are. Keep your browser's developer console open and try each selection and modification yourself on a small test page.

Creating and Inserting HTML Elements Dynamically

Introduction

Up to this point you have mostly worked with HTML that already exists in the page. In this topic you learn to build markup at runtime: JavaScript's document.createElement() produces a new element node that lives in memory, and you then configure it — setting textContent or innerHTML, adding attributes with setAttribute(), assigning classes or an id — before it ever appears on screen. Only when you insert the node into the document with a method such as appendChild(), insertBefore(), append(), prepend(), or insertAdjacentElement() does the browser render it.

This matters because almost every dynamic interface you will build in this course — a list that grows as users add items, a table filled from fetched data, a modal or alert generated on demand — depends on creating and placing elements precisely. Choosing the right insertion method controls where the new content lands relative to a reference element: inside at the end, inside at the start, immediately before, or immediately after. The same techniques let you assemble nested structures (for example, building an li, appending a span and a button to it, and then appending the whole li to a ul) so that a single insertion adds a complete component.

As you watch, pay attention to three things: the exact position each method produces relative to the reference element, the difference between methods that take element nodes and those that accept strings of HTML or plain text, and the fact that you must first select a target element before you can insert anything into it. Try to re-type each example yourself in a scratch page or online editor rather than only watching — insertion order is much easier to remember once you have seen it move content around on your own screen.

Modifying Existing Elements and Their Properties

Introduction

Once you can locate an element in the DOM, the next step is changing it. Nearly every interactive feature you will build in this course — toggling a menu, highlighting a form field with an error, updating a counter, showing or hiding a panel — comes down to reading and writing the properties of elements that already exist on the page. JavaScript gives you several parallel routes to do this: attribute methods such as getAttribute(), setAttribute(), hasAttribute() and removeAttribute(); direct property access such as element.id, element.value or element.src; the style object for inline CSS; getComputedStyle() for reading the styles the browser actually applied; className and the classList API for class manipulation; and textContent, innerText, innerHTML and outerHTML for content.

Knowing which route to use matters. Setting a class is usually better than writing a dozen inline style rules, because it keeps presentation in your stylesheet and your logic readable. Reading element.style only returns inline styles, so getComputedStyle() is the tool when you need the value that is actually in effect. And innerHTML is powerful but inserts markup, which raises both performance and security concerns compared with textContent. Changing dimensions and position through the style object (width, height, top, left, transform) follows the same rules and is how animations and drag-style interactions begin.

The three videos below are from a single, consistent tutorial series, so the examples build on each other. As you watch, pay attention to the distinction between an attribute (what is written in the HTML source) and a property (what lives on the JavaScript object), to when the presenter chooses innerHTML versus a text-only property, and to how classList methods add, remove, toggle and test classes without overwriting the ones already there. Try each snippet yourself in the linked Repl or in your browser console — these techniques only stick once you have typed them.

Removing Elements from the DOM

Introduction

Adding elements to a page is only half of dynamic DOM work. Interfaces built with JavaScript also need to take things away: closing a notification, deleting a row from a table, clearing a list before re-rendering search results, or tearing down a modal when the user dismisses it. This topic covers the methods that do that work — the older parent.removeChild(child) pattern and the newer, simpler element.remove() — along with the related question of how to clear out every child of a container at once.

Removal is never just one line, though. Before you can remove something you have to select the correct target, usually with querySelector(), getElementById(), or by walking up from an event target with closest() or parentNode. After removal, the node is gone from the document, but any references your code still holds — variables, arrays, timers, or event listeners attached to objects that outlive the element — can keep it alive in memory or cause errors. That is why this topic also covers removing event listeners before removal and writing defensive code that checks an element exists (and has a parent) before trying to delete it.

The videos below approach the topic from different angles: one walks directly through removal methods, one focuses on navigating an element's children (the selection skill you need before any removal), and one contrasts removing an element with simply hiding it. While watching, pay attention to which object the method is called on — removeChild() is called on the parent, remove() on the element itself — and notice when a demo hides an element versus actually deleting it from the tree.

Adding and Managing Event Listeners

Introduction

Creating elements with JavaScript only gets you halfway to an interactive page. The other half is listening: deciding which user or browser actions your code should react to, and writing the functions that run when those actions occur. The modern way to do this is addEventListener, a method available on every DOM node (and on window and document) that connects an event type such as click, input, keydown, submit, or scroll to a handler function.

Along the way you will meet the event object that the browser passes into every handler. It carries details like event.target (the element that actually triggered the event), event.currentTarget (the element the listener is attached to), event.type, key and pointer information, and methods such as preventDefault() and stopPropagation(). You will also learn that events travel through the DOM tree in two phases — capturing down from the root, then bubbling back up — and that the third argument to addEventListener (true/false, or an options object with capture, once, and passive) lets you control that behavior. Because listeners can accumulate and leak, removeEventListener and the once option matter for clean code.

The payoff for this module is event delegation: instead of attaching a listener to every button in a list you build dynamically, you attach one listener to a stable parent and use event.target to figure out what was clicked. As you watch the videos below, pay attention to three things: the exact syntax of addEventListener and its options, how the speaker uses the event object to identify the source of an event, and why bubbling is what makes delegation possible at all.

Building Interactive UI Controls with JavaScript

Introduction

Up to this point in the module you have practiced the individual pieces of DOM work: reading the document tree, creating elements, changing styles and content, and responding to events. This topic puts those pieces together. An interactive UI control — a toggle, a tab strip, a custom dropdown, a media panel — is nothing more than a small, well-planned collection of elements that JavaScript builds, wires to event listeners, and keeps in a known state as the user interacts with it.

The work usually follows a predictable order. First you plan the structure: what elements the control needs, how they nest, and what markup roles they play. Then you construct those elements in JavaScript, attach listeners to the parts that respond to input, and decide how the control's state (open/closed, selected, disabled, current value) will be stored and reflected back in the DOM. Finally you make the control accessible — keyboard operable, with ARIA roles and states that describe it to assistive technology — and package the whole thing so it can be reused more than once on a page.

The videos below approach this from two angles. The two project videos follow a small interactive application being built from scratch, so watch how the author moves from markup and layout to the JavaScript that drives behavior, and notice where state is being tracked and where the DOM is being updated in response. The accessibility video addresses the part beginners most often skip: why a JavaScript-built control needs ARIA and semantics to be usable by everyone. While watching, keep asking yourself where each technique would land in your own control's structure, state, and event wiring.
