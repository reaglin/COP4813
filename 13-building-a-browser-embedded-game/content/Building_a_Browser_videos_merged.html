Game Design Fundamentals

Introduction

Before you write a single line of JavaScript, a browser game needs a plan. Game design fundamentals are about answering a handful of deceptively simple questions: What is the player trying to do? What rules govern success and failure? What objects exist in the world, and how do they relate to one another? How does the player act on the game, and what does the game show back? Writing these answers down — in a short design document or a rough sketch — turns a vague idea into something you can actually build in a few weeks.

In this course, design discipline matters mostly because of scope. A browser game built on Canvas with a single game loop can support a surprising amount of play, but only if the entity list stays small, the rules stay clear, and the win/loss conditions are decidable in code. Deciding early that you have a player, a set of obstacles, a score, and two end states makes the later work of looping, rendering, input handling, and collision detection far more straightforward. Changing your mind about the core objective halfway through does the opposite.

The videos below come from game designers rather than web programmers, so treat them as sources of design thinking, not implementation detail. As you watch, listen for how designers talk about a core mechanic, how rules create interesting decisions, and how constraints improve rather than limit a project. Then translate what you hear into your own one-page design: objective, rules, entity list, interaction model, and a sketch of the screen.

Canvas Drawing for Games

Introduction

The HTML5 Canvas element gives you a blank rectangle of pixels in the browser and a JavaScript drawing context (usually obtained with getContext('2d')) that lets you paint on it. Everything a player sees in a Canvas game — the background, the character, the obstacles, the score text — is drawn by your code, one shape or image at a time, and then erased and drawn again a fraction of a second later. There is no DOM element for the player's character; there is only what you drew on the most recent frame.

In this module that matters because Canvas drawing is the output half of your game. You will set up the canvas and its size, establish the coordinate grid (origin at the top-left, x increasing to the right, y increasing downward), layer a background, draw rectangles and images for obstacles and objects, and cut frames out of a sprite sheet with drawImage to animate a character. Then you will clear the canvas with clearRect and redraw everything so that motion appears smooth rather than smeared.

As you watch the videos below, pay attention to a few recurring details: how the canvas is created and sized in HTML versus in JavaScript, how each drawing call translates numbers into positions on screen, the order in which things are drawn (background first, foreground last), and where the clear-and-redraw step sits inside the animation loop. Try pausing and recreating small pieces in your own file — a filled rectangle, an image at a given x and y — before attempting a full game.

Animation and the Game Loop

Introduction

Every browser game, no matter how simple, is driven by a loop: a function that runs over and over, updating the positions and states of game objects and then redrawing the screen. This is the game loop, and it is the heartbeat of the project you are building in this module. Without it, a Canvas drawing is just a static picture; with it, the same drawing code becomes animation.

In JavaScript, the preferred way to drive that loop is requestAnimationFrame. Unlike setInterval or setTimeout, it asks the browser to call your function right before the next repaint, which produces smoother motion, synchronizes with the display's refresh rate, and pauses automatically when the tab is hidden. You will write a core loop function that clears the canvas, updates game state, draws everything, and then schedules itself again. You will also learn to store the loop's ID so you can stop it for pausing or for a game-over screen.

The subtler issue is timing. Because different machines and monitors run at different frame rates, movement expressed as "add 5 pixels per frame" will run faster on some computers than others. The fix is delta time: measure how much real time passed since the last frame and scale movement by it. As you watch these videos, pay attention to three things — how the loop schedules itself, where in the loop state is updated versus drawn, and how timestamps are used to make motion independent of frame rate.

Event Handling and Player Input

Introduction

A game is only a game when the player can act on it. Everything you have built so far — the Canvas drawing calls, the state object, the requestAnimationFrame loop — runs on its own schedule. Event handling is the bridge that lets a keypress, a click, or a finger tap reach into that loop and change what happens on the next frame.

In this topic you will attach listeners to the document or directly to the canvas element, read the properties the browser hands you (key codes and key names from keyboard events, coordinates from mouse events, touch lists from touch events), and convert those raw values into game-meaningful actions such as "move left," "fire," or "aim at this point." A common and important pattern is to record input into a state object rather than acting immediately inside the handler, so the game loop stays the single place where the world updates. You will also learn when to call preventDefault() to stop the browser from scrolling the page, selecting text, or firing a synthetic click when the player is really trying to play.

While watching the videos below, pay attention to three things: which element the listener is attached to, which event properties carry the information you need, and how the handler avoids doing too much work on its own. Mouse and touch coordinates in particular are reported relative to the viewport, so note any step that converts them into canvas coordinates — that conversion is something you will need in your own project.

Game Logic and State Management

Introduction

A game is really just a data structure that changes over time. Behind the sprites and animation sits a game state: the score, the number of lives remaining, the positions and velocities of every entity, and a flag telling you whether the game is running, paused, won, or lost. Every frame of your game loop reads that state, updates it according to the rules, and redraws the screen to match. If the state is clean and well organized, the rest of the game becomes much easier to write, test, and debug.

In this topic you will work through the mechanics that drive those state changes. Collision detection answers the question "did these two things touch?" and usually drives everything else: a hit may increase the score, remove an entity, deduct a life, or end the round. Win and loss conditions are checks you run during the update phase, and restarting the game is simply resetting your state object back to its initial values rather than reloading the page. Keeping all of this in the update phase of one unified loop prevents the scattered, hard-to-trace bugs that come from changing state in random event handlers.

As you watch, pay attention to two things. First, the geometry and logic of rectangle overlap tests: how the comparison is built, and where in the loop it belongs. Second, the broader idea of state that the React videos illustrate: what belongs in state versus what is passed in, why state updates may not take effect immediately, and why you should treat state as something you replace rather than quietly mutate. Those habits transfer directly to a plain JavaScript Canvas game even though the framework differs.

Integrating and Assembling the Complete Game

Introduction

Up to this point you have practiced the pieces of browser game development separately: drawing shapes and images on a Canvas, animating them frame by frame, capturing keyboard and mouse input, and writing the logic that decides what happens next. This topic is about assembly — taking those separate skills and fitting them into one project with a sensible file structure, a single authoritative game loop, and clear rules for when the player wins or loses.

Assembly is where most beginner projects break down, because subsystems that worked in isolation start competing: input events fire at unpredictable times, drawing code is scattered across functions, and state is updated in two places at once. The discipline you are learning here is to keep one loop that clears, updates, and redraws every frame; to let event handlers only record intent rather than directly move objects; and to keep game state in one structure that logic and rendering both read from.

As you watch the videos below, pay less attention to the specific game being built and more to the architecture. Ask yourself: where does this project store its state? What happens exactly once per frame versus once per event? Where do collision checks and scoring live? How does the developer get the finished game onto a page so someone else can play it? Those questions map directly onto the subtopics in this module.
