Introduction

Every change you make in this course travels the same path: you edit a file on your own computer, you record and send that change to GitHub, and then the live site served by GitHub Pages reflects what you sent. Those three stages — local editing, committing and pushing, and live publication — form the local-to-live pipeline. Learning to see them as distinct steps makes it much easier to diagnose problems later: a file saved but not committed, a commit made but not pushed, and a push that hasn't finished rebuilding the site all look different once you know what to check.

This workflow matters here because it is the pattern you will repeat for the rest of the term. Rather than uploading files by hand, you will keep a local copy of your project, use Git to track changes, and let GitHub Pages serve the result at a public URL. The same habits also transfer directly to professional web development, where version control is the normal way teams edit, review, and deploy code.

As you watch the videos below, focus on three things: what a commit actually is (a recorded snapshot, not a save), the difference between committing locally and pushing to a remote repository on GitHub, and where each step happens — in your editor, in your local repository, or on GitHub's servers. Don't worry about memorizing commands on the first pass; aim to build a mental map of the pipeline so the hands-on steps later in the module feel like confirmation rather than guesswork.
