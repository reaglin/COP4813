Introduction

Writing an HTML file on your own computer is only half the job. Until that file is staged, committed, and pushed to GitHub, it exists nowhere but your laptop. This topic walks through the final steps of the local-to-live pipeline: selecting the changes you want to record (staging), saving them as a labeled snapshot with a message (committing), sending that snapshot to your remote repository on GitHub (pushing), and then confirming the result by visiting your GitHub Pages URL in a browser.

Two details trip up most beginners. First, GitHub Pages does not publish instantly — after a push, GitHub runs a short build and deploy process, so a page may take a minute or two to appear or update. Second, your Pages URL is predictable: it is derived from your GitHub username and repository name, so you should know exactly where to look rather than hunting for a link. If the page shows a 404 or stale content, the usual causes are an unpushed commit, a file named something other than index.html, or simply checking too soon.

As you watch these videos, focus on the mechanics rather than memorizing commands. Notice the difference between a file that is modified, staged, and committed; watch where the push button or command appears; and pay attention to how the interface signals that your local branch is ahead of or in sync with the remote. The commit-push-verify loop you see here is the same cycle you will repeat for every assignment in this course.
