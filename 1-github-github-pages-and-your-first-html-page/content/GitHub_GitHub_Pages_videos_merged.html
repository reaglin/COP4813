Introduction to GitHub

Introduction

GitHub is a web-based platform where developers store, share, and collaborate on code. It is built around Git, a version control system that tracks changes to files over time, but GitHub adds hosting, a web interface, issue tracking, and social features like profiles and followers. In this course, GitHub is more than a storage location: it is the place your work lives, the record of your progress, and — through GitHub Pages — the server that will publish your websites to a public URL.

Before you can publish anything, you need an account. Choosing a username matters more than it might seem, because your GitHub Pages site addresses are derived from it and because your profile is often the first thing an employer or collaborator sees. Take a few minutes to pick something professional and readable, then fill in a profile photo, name, and bio so your account looks like it belongs to a real developer rather than an abandoned test account.

As you watch the videos below, look for three things: the distinction between Git (the tool) and GitHub (the service), the basic mechanics of creating a repository where files are stored, and the profile and security settings that make your account usable and safe. You do not need to master every feature shown — focus on the vocabulary and the steps you will repeat all semester.

Creating Your First Repository

Introduction

A repository — usually shortened to "repo" — is the folder GitHub keeps for a single project. It holds your files, a full history of every change you save, and the settings that decide who can see the project. Before you can write a line of HTML for this course, you need a place to put it, and that place is a repository you create and configure yourself.

Creating a repo looks like a short form, but each field matters. You will navigate to the New Repository page, choose a name (which later becomes part of your public GitHub Pages URL), decide between public and private visibility, and choose whether to initialize the repo with a README file. After you click Create, you should be able to recognize that the repository exists, read its landing page, and find the controls for adding files.

While watching these videos, pay attention to where the "New" button lives, how the name field reacts as you type, what the public/private choice actually changes, and what the repository page looks like immediately after creation. Also notice the different ways files get into a repo — drag-and-drop upload, the web editor, and the commit-based GitHub flow — because you will use those methods throughout the module.

Deploying with GitHub Pages

Introduction

GitHub Pages is a free static site hosting service built into GitHub. Once you turn it on for a repository, GitHub takes the files you have committed — HTML, CSS, images — and serves them at a public web address that anyone can visit. There is no server to rent, no FTP client to configure, and no build server to maintain: publishing is simply a matter of pushing your work to the right branch and folder.

This matters in COP4813 because GitHub Pages is the delivery end of the workflow you will repeat all semester. You will edit files locally, commit and push them to GitHub, and then confirm the change appears on your live site. Understanding that the URL is derived from your username and repository name, and that GitHub rebuilds automatically after each push, removes most of the mystery when something does not appear as expected.

As you watch the videos below, pay close attention to three things: where the Pages settings live in the repository (Settings, then the Pages section), which branch and folder are selected as the publishing source, and the exact shape of the resulting URL. Also notice that publication is not instant — there is a short build delay, so a page that looks missing may simply need a refresh a minute later. Interfaces change over time, so expect small differences between what you see on screen and GitHub's current layout; the underlying steps remain the same.

Writing Your First HTML Document

Introduction

Every web page you will build in this course begins as a plain text file with a predictable skeleton. HTML (HyperText Markup Language) is not a programming language; it is a markup language that uses tags to label the parts of a document so a browser knows what each piece of content is. In this topic you will write your first complete HTML file and display the words "Hello, World" in a browser.

The structure you learn here is small but non-negotiable. The DOCTYPE declaration tells the browser to use modern standards mode, the root html element wraps everything, the head element holds information about the page (such as the title shown on the browser tab and the character encoding), and the body element holds everything a visitor actually sees. Getting this minimal structure right matters immediately, because the file you create here is the same file you will commit, push, and publish to GitHub Pages later in the module.

As you watch, focus on three things: the exact order and nesting of the doctype, html, head, and body; which content belongs in the head versus the body; and how opening and closing tags pair up to form elements. Try to pause each video and retype the structure yourself from memory rather than copying it — the goal is to be able to produce a valid blank page without looking anything up.

Publishing and Verifying Your Live Page

Introduction

Writing an HTML file on your own computer is only half the job. Until that file is staged, committed, and pushed to GitHub, it exists nowhere but your laptop. This topic walks through the final steps of the local-to-live pipeline: selecting the changes you want to record (staging), saving them as a labeled snapshot with a message (committing), sending that snapshot to your remote repository on GitHub (pushing), and then confirming the result by visiting your GitHub Pages URL in a browser.

Two details trip up most beginners. First, GitHub Pages does not publish instantly — after a push, GitHub runs a short build and deploy process, so a page may take a minute or two to appear or update. Second, your Pages URL is predictable: it is derived from your GitHub username and repository name, so you should know exactly where to look rather than hunting for a link. If the page shows a 404 or stale content, the usual causes are an unpushed commit, a file named something other than index.html, or simply checking too soon.

As you watch these videos, focus on the mechanics rather than memorizing commands. Notice the difference between a file that is modified, staged, and committed; watch where the push button or command appears; and pay attention to how the interface signals that your local branch is ahead of or in sync with the remote. The commit-push-verify loop you see here is the same cycle you will repeat for every assignment in this course.

Understanding the Development Workflow

Introduction

Every change you make in this course travels the same path: you edit a file on your own computer, you record and send that change to GitHub, and then the live site served by GitHub Pages reflects what you sent. Those three stages — local editing, committing and pushing, and live publication — form the local-to-live pipeline. Learning to see them as distinct steps makes it much easier to diagnose problems later: a file saved but not committed, a commit made but not pushed, and a push that hasn't finished rebuilding the site all look different once you know what to check.

This workflow matters here because it is the pattern you will repeat for the rest of the term. Rather than uploading files by hand, you will keep a local copy of your project, use Git to track changes, and let GitHub Pages serve the result at a public URL. The same habits also transfer directly to professional web development, where version control is the normal way teams edit, review, and deploy code.

As you watch the videos below, focus on three things: what a commit actually is (a recorded snapshot, not a save), the difference between committing locally and pushing to a remote repository on GitHub, and where each step happens — in your editor, in your local repository, or on GitHub's servers. Don't worry about memorizing commands on the first pass; aim to build a mental map of the pipeline so the hands-on steps later in the module feel like confirmation rather than guesswork.
