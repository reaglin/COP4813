What is the DOM?

Introduction

When a browser loads a web page, it does not simply display the HTML file as text. It reads (parses) the markup and builds an in-memory model of the document: a structured collection of objects that represent every element, attribute, and piece of text on the page. That model is the Document Object Model, or DOM. Because it is made of objects, JavaScript can read it, search it, and change it while the page is running.

This topic is the conceptual foundation for the rest of the module and for much of the rest of the course. Before you can select elements, change styles, or add new content with code, you need a clear mental picture of what you are actually working with: a tree of nodes rooted at the document object, with parent, child, and sibling relationships that mirror the nesting of your HTML tags. You should also understand why the DOM exists at all — it is a standardized interface that lets a scripting language talk to a document that was written in a markup language.

As you watch the videos below, look for three things. First, the distinction between your HTML source file and the DOM the browser builds from it, since they are related but not identical. Second, the vocabulary of the tree: document, element nodes, text nodes, attributes, parent and child. Third, how JavaScript reaches into that tree through the document object. Try opening your browser's developer tools alongside the videos and inspect a simple page of your own so the abstract tree becomes something you can see.

The DOM Tree Structure

Introduction

When a browser loads an HTML file, it does not simply display the text: it reads the markup and builds an in-memory model of the page called the Document Object Model. That model is organized as a tree. A single document node sits at the root, element nodes (such as html, body, div, and p) branch out beneath it, text nodes hold the actual words you see on screen, and attribute nodes carry information like id, class, and src that belongs to an element.

Understanding this structure matters because every piece of JavaScript you write later in this course depends on it. Selecting an element, changing its text, adding a class, or inserting a new node all assume you can picture where that node sits in the tree and what is above, below, and beside it. The vocabulary of parent, child, and sibling is how the DOM API lets you move from one node to another, and properties such as parentElement, children, childNodes, firstChild, nextSibling, and previousSibling are the tools for that movement.

As you watch the videos below, keep a specific question in mind: for a given line of HTML, what nodes does the browser actually create? Pay attention to the difference between an element node and the text node inside it, notice how whitespace and line breaks in your source can appear as text nodes, and watch for the distinction between properties that return all node types and those that return elements only. Sketching a small HTML snippet as a tree on paper while you watch is the fastest way to make this concrete.

Selecting DOM Elements

Introduction

Before you can change anything on a page with JavaScript, you have to be able to find the thing you want to change. DOM selection is the process of asking the browser's document object for a reference to one or more elements in the page's node tree. Once you hold that reference in a variable, it becomes your handle for reading content, changing styles, attaching events, or removing the element entirely.

In this topic you will work with the core vanilla JavaScript selection methods: getElementById for a single element with a unique id, querySelector for the first element matching any CSS selector, and querySelectorAll for a static list of all matching elements. You will also practice scoped selection, which means calling querySelector or querySelectorAll on an element reference instead of on document so the search is limited to that element's descendants. This is how you avoid accidentally grabbing the wrong card, row, or button on a page with repeated markup.

As you watch, pay attention to three things. First, the return value of each method: a single element, null when nothing matches, or a NodeList that may be empty. Second, the CSS selector syntax being passed in, since querySelector accepts the same selectors you already write in stylesheets. Third, how the presenter checks the result in the console before using it, because reading and verifying your selection is what prevents the null-reference errors that break scripts further down the file.

Manipulating DOM Elements

Introduction

Once you can select an element from the DOM, the next step is to change it. Every element node exposes properties and methods that let JavaScript read and rewrite what the user sees: the text inside an element, the markup it contains, its attributes (such as src, href, id, or data-* values), the CSS classes applied to it, and its inline style declarations. This topic covers that toolkit — textContent and innerText, innerHTML and outerHTML, getAttribute/setAttribute, the classList API (add, remove, toggle, contains), the style object, and getComputedStyle for reading the styles the browser actually resolved.

This matters in COP4813 because almost every interactive feature you build — showing a validation message, highlighting a selected row, disabling a button, swapping an image — is some combination of these operations. It also matters for correctness and safety: writing to innerHTML parses a string as HTML and can introduce security and performance problems, while textContent treats the same string as plain text. Knowing which property to reach for is part of writing professional front-end code.

As you watch, pay attention to three things. First, the difference between properties that read or write text and those that read or write markup, and when each is appropriate. Second, the distinction between an element's inline style (what you set through .style) and its computed style (what the browser resolves from all stylesheets). Third, why toggling a CSS class is usually preferable to setting many inline styles one at a time — it keeps presentation in your CSS and behavior in your JavaScript.

Adding and Removing DOM Nodes

Introduction

So far in this module you have learned to find elements that already exist on the page and change their text, attributes, styles, and classes. This topic goes a step further: instead of only editing what the browser built from your HTML, you will build new nodes in JavaScript and attach them to the document yourself. That is how interactive pages add a new to-do item, render a list of search results, show a notification banner, or delete a row when a user clicks a button.

The workflow is usually the same three steps. First, create a node in memory with document.createElement() (or clone an existing one with cloneNode()). Second, give it content and configuration by setting textContent, innerHTML, or attributes such as id, class, and src. Third, attach it to the tree with appendChild(), append(), insertBefore(), or insertAdjacentElement(), depending on exactly where it must land. Removal and swapping follow the same logic in reverse, using removeChild(), the simpler element.remove(), and replaceChild() or replaceWith().

While watching the videos, pay attention to two things. First, notice that a created element does nothing visible until it is inserted into the document — forgetting that insertion step is the most common beginner bug. Second, watch the difference between the older parent-based methods (parent.appendChild(child), parent.removeChild(child), parent.replaceChild(new, old)) and the newer child-based ones (append(), remove(), replaceWith()), and note which ones accept text strings and multiple arguments. Also keep an eye on when innerHTML is a convenient shortcut and when it is risky compared with building nodes explicitly.
