Introduction to Browser Animation

Introduction

Animation in the browser is the controlled change of visual properties over time: an element fades in, a menu slides open, a chart bar grows, a loading spinner rotates. Behind every one of these effects is the browser's rendering pipeline, which recalculates styles, lays out elements, paints pixels, and composites layers — ideally fast enough to produce a new frame roughly every 16.7 milliseconds (60 frames per second). Understanding that pipeline is what separates animation that feels polished from animation that stutters.

Animation matters in this course because it is a user experience tool, not decoration. Motion communicates state changes, directs attention, confirms that an action registered, and makes transitions between views feel continuous rather than abrupt. Used carelessly, it does the opposite: it distracts, delays interaction, and drains battery on mobile devices.

There are two primary approaches you will work with. CSS-based animation (transitions and @keyframes) is declarative — you describe the start and end states and let the browser handle the frames, often on the compositor thread for free performance. JavaScript-driven animation (typically using requestAnimationFrame) is imperative — you compute values frame by frame, which costs more but buys you control over physics, user input, and dynamic conditions. As you watch these videos, pay attention to three things: which properties are being animated, who is deciding the value of each frame, and what the speaker says about when to pick one approach over the other.

CSS Transitions

Introduction

CSS transitions are the simplest way to make a web page feel alive. Instead of a property snapping instantly from one value to another when a state changes — for example on :hover, :focus, or when a class is added by JavaScript — a transition tells the browser to interpolate between the old and new values over a span of time. The result is motion that communicates change to the user without writing a single line of animation code.

In this module you will work with the four sub-properties that control that motion: transition-property (which properties are allowed to animate), transition-duration (how long the change takes), transition-timing-function (the acceleration curve, such as ease, linear, ease-in-out, or a custom cubic-bezier), and transition-delay (how long to wait before starting). You will also use the transition shorthand to combine them, and you will learn that not every CSS property is transitionable or cheap to animate — properties like transform and opacity are handled by the compositor, while animating width, height, or top forces the browser to redo layout and paint work on every frame.

As you watch the videos below, pay attention to three things: the exact syntax and ordering of values in the shorthand, where the transition declaration is placed (on the base state, not only on the hover state, so it applies in both directions), and any remarks about which properties are safe to animate. Keep a scratch HTML file open and reproduce each example yourself — transitions are far easier to understand by tweaking a duration or timing function and watching the difference than by reading about them.

CSS Keyframe Animations

Introduction

CSS keyframe animations let you describe a sequence of style changes over time without writing any JavaScript. You define the sequence once with the @keyframes rule — naming it and listing the states the element should pass through at 0%, 50%, 100%, or using the from and to shorthands — and then attach that named sequence to an element with the animation property. Unlike a transition, which only runs when a value changes, a keyframe animation can run on page load, repeat indefinitely, and move through many intermediate steps.

In this course the keyframe animation is your main declarative animation tool, and the real learning is in the sub-properties that control how the sequence plays: animation-duration and animation-delay for timing, animation-timing-function for easing (including steps() for frame-by-frame effects), animation-iteration-count for repetition, animation-direction for normal, reverse, and alternate playback, animation-fill-mode for what styles apply before the animation starts and after it ends, and animation-play-state for pausing and resuming.

As you watch, pay attention to three things. First, the exact syntax of a @keyframes block and how percentages map to points in the timeline. Second, how each sub-property changes the visible result — try predicting the outcome before the instructor shows it. Third, which CSS properties are being animated: properties like transform and opacity are cheap for the browser to animate, and that choice connects directly to the performance material later in this module.

JavaScript-Driven Animation with requestAnimationFrame

Introduction

CSS transitions and keyframe animations are excellent for declarative, predictable motion, but some animations need to be computed frame by frame — physics, collisions, values that depend on user input, or drawing on a canvas. That is where requestAnimationFrame (often shortened to rAF) comes in. It asks the browser to call a function just before the next repaint, so your updates land in step with the browser's own rendering cycle instead of fighting it.

The core pattern is simple and worth memorizing: write a function that updates state and applies it to the DOM or canvas, then call requestAnimationFrame again from inside that function to schedule the next frame. The callback receives a high-resolution timestamp, which you use to compute elapsed time (delta time) so motion stays consistent regardless of the device's frame rate. Saving the ID returned by requestAnimationFrame lets you stop the loop later with cancelAnimationFrame — a detail many beginners skip and then wonder why animations keep running in the background.

As you watch these videos, pay attention to four things: where the loop re-schedules itself, how time is handled, which properties are being changed each frame, and how the speaker contrasts rAF with setInterval or setTimeout. The timer-based approach can drift, fire while the tab is hidden, and produce frames the browser never paints; rAF avoids all three. Try pausing each video and rebuilding the loop yourself before watching the finished result.

Animation Performance and Best Practices

Introduction

Animation on the web looks simple from the outside — an element slides, fades, or spins — but underneath, the browser is doing a surprising amount of work on every single frame. To hit a smooth 60 frames per second, the browser has roughly 16 milliseconds to recalculate styles, lay out the page, paint pixels, and composite layers onto the screen. When your animation forces the browser to redo expensive stages of that pipeline too often, frames get dropped and the motion feels janky.

This topic focuses on the performance side of animation: understanding the rendering pipeline (style, layout, paint, composite), knowing which properties the GPU can animate cheaply (transform and opacity) versus which trigger layout or paint, avoiding layout thrashing caused by interleaved DOM reads and writes, deciding when CSS animation is the better tool and when a JavaScript requestAnimationFrame loop is needed, and using Chrome DevTools to measure rather than guess.

The two videos below approach this from different angles. The first builds background intuition about how a browser gets from a URL to rendered pixels, which is the context the rendering pipeline sits inside. The second is a practical refresher on CSS animation syntax and properties — useful because so many performance recommendations boil down to "let CSS and the compositor do the work when you can." As you watch, keep asking: which properties are being animated here, and which stages of the pipeline would they trigger?
