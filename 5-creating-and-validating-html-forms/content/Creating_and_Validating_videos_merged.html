Introduction to HTML Forms

Introduction

HTML forms are the primary way that web pages collect information from people: a search box, a login screen, a checkout page, and a survey are all forms. At its core, a form is a container element, <form>, that groups a set of controls (text boxes, checkboxes, radio buttons, drop-down lists, buttons) and defines what should happen when the user submits them. Two attributes on the <form> element do most of that work: action, which names the URL that will receive the data, and method, which says how the data travels (most commonly GET or POST).

In this course, forms are the bridge between the browser and server-side processing. Before you can validate input or handle it in application code, you need a clear mental model of form structure: the <form> wrapper, the controls inside it, the name attribute that labels each piece of submitted data, the <label> elements that connect text to controls, and the submit button that triggers the request. Getting this structure right from the start makes later work on accessibility and validation far easier.

As you watch the videos below, pay attention to a few things: how the <form> tag is opened and closed and what sits inside it, where action and method appear and how they are described, how each input is given a name and an associated label, and how different input types change what the user sees and what gets sent. Try typing along with at least one example rather than only watching.

Form Input Types and Elements

Introduction

Forms are the main way users send data to a web application. Every search box, login screen, checkout page, and survey is built from the same small set of HTML elements: the form element itself, plus input, select, option, textarea, button, and label. What makes forms interesting is that a single element — input — changes behavior entirely based on its type attribute, producing anything from a simple text box to a date picker, a color swatch, a file chooser, or an invisible field that carries data the user never sees.

In this course, this topic is the foundation for everything that follows in the module. Before you can validate input, choose between GET and POST, or wire up the Constraint Validation API in JavaScript, you need to know which control to reach for and how to mark it up correctly. Choosing the right input type is also your first accessibility and usability decision: type="email" and type="tel" change the on-screen keyboard on mobile devices, radio buttons communicate mutually exclusive choices, and a properly associated label makes a control usable with a screen reader or by clicking the text next to it.

As you watch the videos below, pay attention to a few recurring details: how the name attribute (not the id) determines what gets submitted, how label and id are paired, how radio buttons in the same group share a name while checkboxes usually do not, and how select/option differ from a list of radios. Try pausing and rebuilding each example yourself — a registration or contact form that uses text, password, email, radio, checkbox, select, textarea, and submit is a good practice target.

Labels, Fieldsets, and Form Accessibility

Introduction

A form is only usable if every control tells the user what it is for. The label element is the HTML mechanism that creates that connection: it attaches visible text to a specific input so that screen readers announce the right name, and so that clicking the text moves focus into (or toggles) the control. You can associate a label explicitly, by matching the label's for attribute to the input's id, or implicitly, by nesting the input inside the label element. Both approaches are valid, but explicit association is generally safer and easier to style.

Some controls only make sense as a set. Radio buttons for a shipping method, or checkboxes for a list of interests, need a group-level question in addition to individual labels. That is the job of fieldset, which wraps related controls, and legend, which supplies the group's name. Without them, a screen reader user may hear "Standard, radio button" with no idea what question is being answered.

As you watch the videos below, pay attention to three things: how each presenter writes the markup (for and id pairs, nested labels, fieldset and legend structure), how assistive technology announces a labeled versus an unlabeled control, and the common mistakes they warn against, such as using placeholder text as a substitute for a label, mismatched or duplicated id values, or relying only on visual proximity. These same habits carry directly into the validation work later in this module, since error messages also need to be tied to the control they describe.

Form Submission and Action Attributes

Introduction

A form is only useful if the data it collects actually reaches somewhere. That delivery is controlled by a small set of attributes on the form element: action tells the browser where to send the data, method tells it how to send it (most commonly GET or POST), and enctype tells it how the data should be encoded on the way. Together these three attributes determine the shape of the HTTP request your server receives.

In this course the distinction matters because you will build both the front end and the code that consumes the submitted data. GET appends name/value pairs to the URL as a query string, which makes it visible, bookmarkable, cacheable, and limited in length — fine for searches and filters, wrong for passwords or anything that changes state. POST places the data in the request body, which suits larger payloads, sensitive values, and file uploads. File uploads in particular require enctype set to multipart/form-data, while the default application/x-www-form-urlencoded handles ordinary text fields.

As you watch the videos below, pay attention to three things: what the URL looks like after submission, what the request actually contains, and which attribute combination the presenter uses for each scenario. Also notice how submission is triggered — a submit button, the Enter key inside a text input, or JavaScript — because later in this module you will intercept that moment to run validation.

Built-in HTML5 Validation Attributes

Introduction

HTML5 gives you a surprising amount of validation power before you write a single line of JavaScript. By adding attributes directly to your input elements — required, minlength, maxlength, pattern, min, max, and the input type itself — you tell the browser what counts as acceptable data, and the browser enforces it at submission time with built-in error messages. This is called constraint validation, and it is the foundation layer that any custom JavaScript validation you write later should build on, not replace.

In this course, built-in validation matters for two reasons. First, it is the cheapest possible way to protect data integrity and guide users: a single required or type="email" attribute catches a large share of common mistakes. Second, it is accessible by default — browsers surface these constraints to assistive technology and handle focus management for you, which is harder to get right by hand. Remember, though, that client-side validation is a usability feature, never a security boundary; server-side validation is still mandatory.

As you watch the videos below, pay attention to a few things: which attributes apply to which input types (minlength and maxlength work on text-like fields, while min and max work on numbers and dates), how pattern uses a regular expression that must match the entire value, and how title supplies the hint text that browsers show when a pattern fails. Also notice the difference between placeholder (a disposable example inside the field) and a real label — placeholder is a hint, not a substitute for labeling.

Custom JavaScript Form Validation

Introduction

HTML5 validation attributes like required, pattern, and min cover many common cases, but real applications often need more: passwords that must match, fields that are required only when another option is selected, usernames checked against a format your business defines, or error messages worded for your users rather than the browser's defaults. Custom JavaScript validation fills that gap. Using the Constraint Validation API (properties and methods such as validity, checkValidity(), and setCustomValidity()) together with event listeners, you can intercept form submission, run your own validation functions, and decide exactly what the user sees and when.

In this module you are building on the semantic, accessible forms from earlier topics, so the goal is not just "stop bad data" but "tell the user clearly what went wrong." That means inline error messages placed near the field they describe, markup that screen readers can announce (labels, aria-describedby, aria-invalid, live regions), and a feedback strategy that balances on-submit checking with real-time input and blur events so users are not scolded mid-typing. Finally, you will see why it pays to organize this logic into a reusable validation module instead of copy-pasting the same if-statements for every field.

The three videos below walk through practical implementations. As you watch, pay attention to the HTML structure that makes inline errors possible (where the error container sits relative to the input), which events the author listens for, how error text is added and cleared, and where the demonstrated approach could be improved for accessibility or reuse. Treat the code as a starting point you will refactor, not a final answer.

Validation Feedback and User Experience

Introduction

A form that rejects input without explaining why is a dead end for the user. Validation feedback is the layer of messaging and visual cues that tells someone what went wrong, where it went wrong, and how to fix it. In this topic you will look at inline error messages placed next to the field they describe, visual indicators of field state (valid, invalid, required, focused), and the trade-offs between validating as the user types versus waiting until submit.

You will also work with the HTML5 Constraint Validation API, which gives you programmatic access to validity states and lets you replace the browser's default bubble messages with your own styled, well-placed text. Because error text that is only visible is not enough, the topic extends into accessible error announcements using ARIA attributes such as aria-invalid, aria-describedby, and live regions, plus summary error lists at the top of long or complex forms. Finally, you will consider when placeholder text helps and when it quietly hurts, and how persistent helper text is usually the safer choice.

The three videos below come from Pope Tech, a producer focused on web accessibility testing. They approach the topic from the evaluation side: how to check whether a form actually communicates its errors to all users, what ARIA is really for, and how an automated tool reports form problems. While watching, pay attention to the checks being performed and ask yourself how you would build a form that passes them the first time, and note any guidance about labels, error identification, and ARIA misuse that you can apply to your own validation code.
